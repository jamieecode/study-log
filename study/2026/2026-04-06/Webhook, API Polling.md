# Webhook, API Polling

## 1. Webhook이란?

데이터가 변경되었을 때 **실시간으로 알림을 받을 수 있는 HTTP 기반 콜백 메커니즘**

- 특정 이벤트가 발생하면 서버가 미리 등록된 URL로 HTTP 요청을 보내 이벤트 데이터를 전달한다.
- Webhook이라는 용어는 2007년 Jeff Lindsay에 의해 처음 사용되었다.
- ex) 푸시 이벤트 알림, 메시지 알림, 결제 시스템(예: 결제 완료 콜백), CI/CD 배포 완료 알림

---

## 2. Webhook 동작 방식

### 클라이언트 설정

- 서버에 **이벤트를 수신할 고유 URL(Endpoint)** 을 등록 및 수신하고 싶은 **이벤트 종류**를 선택

### 이벤트 발생

- 서버에서 특정 이벤트 발생
    
    ex. 예: 결제 완료, 회원 가입, 배포 성공
    

### 서버 → 클라이언트로 HTTP 요청 전송

- 서버는 등록된 URL로 POST 요청을 보내고 이벤트 데이터를 Body에 담아 전달

→ Webhook은 "클라이언트가 요청하는 구조"가 아니라 "서버가 먼저 알려주는 구조"

---

## 3. Webhook vs API Polling

### API Polling이란?

클라이언트가 주기적으로 서버 API를 호출하여 이벤트 발생 여부를 확인하는 방식

보통 60~120초 간격으로 호출한다.

---

### 차이점 비교

| 구분 | Webhook | API Polling |
| --- | --- | --- |
| 통신 방향 | Server → Client | Client → Server |
| 실시간성 | 높음 | 낮음 (주기 의존) |
| 서버 부하 | 낮음 | 높음 (반복 호출) |
| 네트워크 비용 | 효율적 | 비효율적 |
| 구현 난이도 | 비교적 높음 | 비교적 단순 |

---

### Polling의 문제점

- 이벤트가 없더라도 계속 요청 발생
- 서버 리소스 낭비
- 네트워크 트래픽 증가
- 실시간 처리 어려움

---

## 4. Webhook의 장점

- 실시간 이벤트 처리 가능
- 불필요한 API 호출 감소
- 서버 리소스 절약
- 이벤트 기반 아키텍처에 적합

---

## 5. Webhook의 단점 및 고려사항

- 클라이언트 서버가 항상 외부에서 접근 가능해야 함
- 보안 처리 필요 (Signature 검증, Secret Key 등)
- 실패 시 재시도 전략 필요
- 순서 보장 문제 발생 가능
